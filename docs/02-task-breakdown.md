# Task breakdown: how the coding agents were directed

Raw working notes. Each task below is what an agent received: the goal, the spec, and acceptance criteria written as checks the agent had to run and paste back. Agents worked under `CLAUDE.md` (think first, simplest code, surgical changes, prove it with a check).

## Phase 0. Shared context before any agent started

I read the brief, the README rules and all 40 emails myself, ran a script that priced every email against the ERP, and wrote `CONTEXT.md` for the agents: the rules, my first read of each email, the stock contention for the day (HPS-1302 and HPS-1405 short, HPS-1408 exactly used up), the open product questions, and a starting point for the autonomy line. Reason: three agents reading 40 emails separately would disagree on facts before they disagreed on design.

## Phase 1. Three agents in parallel, then review

**A1. Architecture and product agent**
- Goal: product brief, architecture, tool catalog, autonomy policy, golden labels for all 40 emails, task list for the build.
- Spec excerpt: "Every number in the golden labels is recomputed from erp.sqlite by a script. The labels become the eval set, so they must be correct. Decide where the autonomy line sits and enforce it by capability and deterministic code, not by prompt."
- Acceptance: labels generated by a script that exits non-zero if any hand label disagrees with the ERP; copy lint returns zero findings (no em dashes, banned words, antithesis); brief fits two pages.

**A2. UI and UX agent (Claude Design)**
- Goal: the review console as a design canvas plus a token file.
- Spec excerpt: "Use real data from the data pack, never placeholder text. Show the ticket page for E001, E006, E012, E019, E005 and E024. Risk must be visible before the click: what changes in the ERP, stock, credit after, who is notified."
- Acceptance: screens S1 to S9 present; five states (loading, empty, partial, error, success) for the queue and the proposal panel; every contrast pair computed, not guessed, and at AA.

**A3. QA reviewer (independent, five rounds)**
- Goal: find what is wrong. Recompute the labels with its own script, try to break the auto-commit lane, verify every version, price and limit claim against the vendor's own pages.
- Acceptance per round: findings ranked blocker, major, minor, nit, each with file, evidence and exact fix; a close-out table for every earlier finding.

What the reviewer caught that changed the build is in `05-results-and-agent-log.md`.

## Phase 2. Build tasks given to the coding agent

**B1. Data load**
- Spec: Postgres schema mirroring the ERP CSVs, plus emails, cases (tickets), comments, outbox, audit_events, users, sessions. Loader reads `data/erp/*.csv` and `data/emails.jsonl`, numbers tickets HP-1001 upward by arrival time.
- Accept: `npm test` loads 40 emails; `inventory.available >= 0` enforced by a CHECK constraint.

**B2. Email reader without a model** (`src/extract.js`)
- Spec: detect intent; read SKU lines in four layouts (`HPS-1408 x 4`, `HPS-1103 - 15 cases`, CSV, SKU in brackets); read free-text lines ("4 cs hand sanitizer refills", "Dinner napkins - 10 cs", "a box of foil"); keep a `Label:` prefix as a ship-to hint; capture exclusions ("skip the towels"), PO, SO, stated prices, dates, "same as last time".
- Accept: print the extraction for all 40 emails and read it before wiring anything else. Not a quantity: sizes (33 gal, 16oz, 9x9), percentages, parts of codes (BV-0420), "a large outdoor event".
- Do not: guess a unit. If a case-sold item is written in boxes or bags, it is a question.

**B3. Product matcher** (`src/algo.js`, `src/agent.js`)
- Spec: exact SKU first; unknown SKU, try edit distance 1 and confirm with the description; free text, BM25 over name and category with synonyms (big to jumbo, bolsas to liner, talla L to large). A product's main noun (glove, cup, lid) missing from the phrase costs score. Ties within 10% are ambiguous and become a question. Discontinued items only win when clearly named.
- Accept: `test/algo.test.mjs` passes; "the big toilet paper rolls" gives HPS-1104; "33 gal bags" gives HPS-1201; HPS-1035 gives HPS-1305; "gloves" alone is ambiguous between three active SKUs.

**B4. Checks and lanes** (`processEmail`)
- Spec: eleven checks as data (`code`, `label`, `pass`, `detail`). Auto-commit only if all pass. Waiting on customer only if the open issues are questions and none is severe. Everything else needs review, with the approver role set (credit for credit and price, admin for injection).
- Accept: smoke test asserts exactly E001, E003, E015, E038 auto-commit; no other email reaches the ERP; lane agreement with the golden labels printed.

**B5. Commit code** (`commitProposal`)
- Spec: one transaction; lock the ticket, the customer and each inventory row; re-read status, price and stock; new order, change (OPEN or unshipped quantity only) or cancel (OPEN only, release allocation); credit computed after the writes; refuse with every reason at once; idempotent on a second call; audit row inside the same transaction.
- Accept: E019 refused (discontinued); E006 refused for ops, accepted for credit with a reason; E017 sets SO-24055 to CANCELLED and returns 20 cases of HPS-1201; E004 changes SO-24051 HPS-1103 to 25; a second commit of E001 returns `already: true`.

**B6. Tickets**
- Spec: status (new, open, waiting on customer, resolved, closed), priority from flags and dates, due time from priority, assignee, internal notes, replies to an outbox, conflict check with a row version.
- Accept: sending a reply moves the ticket to waiting on customer; a stale row version returns 409 with a reload message.

**B7. Sign-in and roles**
- Spec: Argon2id, httpOnly cookie, hashed token at rest, one hour idle and 24 hours absolute, lockout after five failures, Origin check on writes, role checks on the server for every action.
- Accept: CI signs in through the API; ops gets 403 on a credit release.

**B8. Queue API**
- Spec: views, Gmail-style operators, inverted index search with prefixes, filters with facet counts, stable multi-key sort, pages of 25, Work next from a min-heap.
- Accept: `priority:urgent` returns the four urgent tickets; `sku:HPS-1408` returns only tickets with that SKU.

**B9. Console**
- Spec: Material 3 shapes, Google Sans Flex, navy, sky blue and white, Material Symbols as an inline sprite; navigation drawer that collapses to a rail; sign-in page with role cards; ticket page with the consequence block; stock, audit and results pages; keyboard `/ j k Enter Esc n`.
- Accept: screenshots at 1440 and 390 wide, no horizontal scroll at 390, no console errors other than the expected 401 before sign-in.

**B10. Deploy**
- Spec: Vercel with `public/` static and `api/index.js` as the function; Postgres through the Neon integration; GitHub Actions for tests and a boot test against Postgres 17; first request seeds once even with parallel instances.
- Accept: CI green; the live URL signs in and shows 40 tickets.
